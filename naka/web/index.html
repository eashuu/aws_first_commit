Data-loss prevention for the AI era

Your agent doesn't leak a database. It leaks one field at a time.

A dozen innocuous tool calls, each one individually reasonable, each one individually approved — and between them they have reconstructed a person. Naka authorizes every call with Cedar, scans what comes back, and charges each disclosed field against a running per-subject budget, so the tenth call knows what the first one already gave away.

CALL 01 — allowed

It starts with a name.

An analyst asks the agent to look up a support ticket. The agent calls fetch_customer. A name and a city come back. Nothing here is sensitive, and every DLP product on the market agrees.

CALL 02 — allowed

Then a phone number.

Different tool, different turn, same person. On its own it is a support contact detail. A per-call scanner sees one phone number and lets it through, because one phone number is not a breach.

CALL 03 — allowed

Then a partial address.

The agent reads the shipping record to answer a delivery question. Three fields now. Still nothing any individual policy would stop — and this is exactly where per-call thinking runs out.

CALL 04 — allowed, and now it matters

Then a date of birth.

Name, phone, address, date of birth. That is a re-identifiable individual and a working answer to most bank security questions. No single call did anything wrong. The sequence did.

CALL 05 — withheld at Q2

Naka has been counting.

Every field released about cust_8814 was written to a cumulative, grow-only ledger keyed by principal and subject. The budget is three. The fourth field comes back as [AADHAAR_1] — a numbered placeholder, not a value.

CALL 06 — denied at Q3

And the placeholder is not a loophole.

The agent tries to send its summary to an external endpoint, passing the placeholder along. Restoring a masked value into an outbound argument is its own authorization question, bound to the destination. Denied. Without that, the guardrail becomes the exfiltration channel.

One platform, three egress paths

Data leaves your company through three doors. Most tools watch one.

Naka is a single Cedar policy bundle and a single disclosure ledger, enforced at all three. A subject's budget spent by an agent is the same budget an employee's paste is charged against — because it is the same person's data either way.

The decision model

Three questions, asked on every single call

Most guardrails ask the first one and stop. The leak lives in the second and the third, and answering them is the whole product.

Q1

May this call happen?

Cedar authorizes the tool invocation itself, before it runs. Principal, action, resource, context. A denied call never executes — and still lands in the audit trail, because a refusal is evidence too.

Q2

May this principal learn this field?

Every detected entity is authorized separately, against the ledger of what this principal has already learned about this subject. Denied fields become numbered placeholders the model can still reason about.

Q3

May this value be restored?

Rehydrating a placeholder into an outbound argument is its own Cedar question, bound to the destination. Plaintext lives in a process-local vault for the length of one invocation and is never written anywhere.

Integration

Four lines, and your agent is guarded.

Naka attaches to the Strands Agents SDK as an interceptor. You do not restructure your agent, you do not proxy your model, and you do not move your data. The guard sits between the tool and the transcript, which is the only place where it can see both what was asked and what came back.

01

Attach the hook

One interceptor on the agent's tool boundary. Every invocation and every result passes through it.

02

Point it at a policy bundle

Cedar text, versioned and ETag-guarded. Edit it in the console and the next call picks it up — no redeploy.

03

Watch the ledger fill

A grow-only set per (principal, subject), updated with an atomic DynamoDB ADD, so concurrent calls cannot race each other into over-disclosure.

agent.py 
# The guard is a Strands interceptor. It sees every tool call
# and every tool result — which is the only vantage point from
# which Q2 can be asked at all.

from naka import DisclosureGuard, AuditHook

guard = DisclosureGuard(
    policy   = "s3://naka-policy/agent.cedar",
    ledger   = "dynamodb://naka_audit",
    budget   = 3,            # fields per subject, per principal
    on_error = "deny",       # fail closed. always.
)

agent = Agent(
    tools = [fetch_customer, read_attachment, send_summary],
    hooks = [guard, AuditHook()],
)

# From here the agent is unchanged. It just cannot
# over-disclose any more.
agent("Summarise the KYC file for cust_8814")
What you get

Built like an audit system, not like a demo

Every decision is evidence. Every failure mode was chosen deliberately.

Fails closed, on purpose

If a detector is unreachable, the field is withheld — not released with a warning. The one place Naka is allowed to be unavailable is the one place it is not allowed to be wrong.

No plaintext, anywhere

Detected values live in a process-local vault for the length of one invocation. They are never persisted, never logged, never serialized. The audit API has no field that could carry one.

Three tiers, unioned

Local deterministic checks, then Comprehend, then Nova Pro multimodal. Later tiers only ever add findings. A slower model can never un-detect what a checksum already proved.

Grow-only ledger

The disclosure set is a G-Set updated with an atomic DynamoDB ADD on a string set. Two concurrent calls cannot race each other past the budget, and nothing can be quietly un-disclosed.

Policy as text, versioned

Cedar source, editable in the console, ETag-guarded against lost updates, versioned on every save. Roll forward by editing; roll back by pasting. No deploy in the loop.

Every refusal is evidence

Denied calls are written to the audit table with the same rigour as allowed ones, including which policy clause refused and which tiers ran. A DPDP enquiry is answered from the table, not from memory.

Questions a technical buyer actually asks

The honest answers

A scanner is stateless: it looks at one payload and decides. That is genuinely useful and Naka contains one — three of them, in fact.

The difference is the ledger. A scanner asked the same question twenty times gives the same answer twenty times, which is precisely how an agent walks out with a complete record one innocuous field at a time. Naka's Q2 is a function of history, not just of content, so the twentieth answer differs from the first.

The field is withheld and the call is marked degraded in the audit row, naming which tier was unavailable. It is not released with a logged warning, because a warning nobody reads is indistinguishable from no control at all.

This is the one place in the product where you will see red: a tier that could not run is a fault, not a policy decision. A blocked field is amber, because blocking is Naka working correctly.

Yes, because the placeholders are numbered and stable within a session. [AADHAAR_1] is a token the model can carry through its reasoning, compare against [AADHAAR_2], and pass back into a later tool call.

That last part is why Q3 exists. If a placeholder can be handed to a tool and silently restored, the masking bought you nothing — so restoring one is a separate authorization decision bound to where the value is going.

Because a policy you cannot reason about is a policy you cannot defend to a regulator. Cedar is analysable: you can ask whether one policy is strictly more permissive than another and get an answer, which YAML and imperative rule code cannot offer.

It also means the same bundle governs all three planes. An exemption written for the compliance role applies whether the request came from an agent, a laptop paste or a file scan.

Everything runs in ap-south-1. The audit table stores entity types and counts — that a PAN was withheld, never which PAN. The before/after panes in the console are reconstructed from those counts, which is why the API has no field that could carry a plaintext value even if something went wrong upstream.

Multi-tenant authentication and per-org isolation are not implemented; the console is a single-tenant operator surface secured by a shared key on the write path. Endpoint fleet enrolment is manual. Billing is not wired to anything.

The guardrail itself — Cedar, the three tiers, the ledger, the vault, the audit trail — is real, deployed and running, and the console reads from it live. We would rather tell you which half is which.
