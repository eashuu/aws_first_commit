Plane 02 · Endpoint DLP

The leak that never touches your network.

An employee pastes a customer record into a consumer chatbot from a laptop at home. Your network appliance sees nothing, because there is no network to see it on. Naka's endpoint agent sits on the machine, terminates TLS locally, and inspects the payload before it reaches the wire.

Why the endpoint

The three egress paths a network appliance cannot see

Not because it is badly configured. Because the traffic never crosses it.

Paste into a consumer AI tool

A customer record, a support transcript, a spreadsheet column. The single most common AI data-loss event in practice, and the hardest to see, because it looks exactly like normal browsing.

Upload to personal storage

A file dragged into a personal cloud drive over the employee's own connection. The bytes leave the machine encrypted and go somewhere your DLP has no relationship with.

A prompt typed into a browser extension

Extensions post directly to their own endpoints. There is no corporate proxy in that path and there never will be — the only vantage point is the device itself.

How it works

Local interception, shared policy

01

A local proxy with its own root CA

The agent installs a root certificate on the machine and mints leaf certificates for the hosts it inspects. This is a genuine TLS-interception capability and it is stated plainly rather than buried: install it only where you intend to, and the console gives you the uninstall command next to the install one.

02

The same three detector tiers

Tier 1 runs entirely on-device, so an Aadhaar or PAN is caught with no network round trip and no latency the user can feel. Tiers 2 and 3 are consulted for content that warrants them.

03

The same Cedar bundle

Not a second policy language, not a separate console, not a different set of exemptions to keep in sync. An exemption written for the compliance role applies whether the request came from an agent, a laptop paste or a file scan.

04

An inline overlay, at the moment of the paste

Not an email the next morning. The user is told which entity types were found and why the action was held, while they still have the context to do something about it.

interceptor.js 
// Outbound request bodies are inspected before the socket
// to the real host is ever opened.

proxy.on('request', async (req, res) => {
  const body    = await readBody(req)
  const found   = await detectors.scan(body)   // tier 1 local
  const verdict = await cedar.authorize({
    principal:   session.user,
    action:      'egress::paste',
    resource:    req.headers.host,
    context:     { entities: found.types },
  })

  if (verdict.decision === 'Deny') {
    overlay.warn(found.types, req.headers.host)
    return res.writeHead(403).end()
  }
  forward(req, res)
})
Straight answer

What is built, and what is not

This plane is the least finished of the three. Here is the line, drawn honestly, because you will find it yourself in about ten minutes otherwise.

✓

Built and running

The local agent, the TLS-terminating proxy with its own CA, on-device tier-1 detection, the Cedar evaluation path, and the inline overlay. This has been run end to end on a real machine with live TLS interception, not mocked.

○

Not built

Central enrolment, fleet telemetry and device inventory. The console's Endpoint view therefore shows zero endpoints and says why, rather than rendering a fleet table that does not correspond to anything. Policy distribution to endpoints is manual.

!

Provenance

The endpoint agent began as a separate codebase and was brought under Naka: rebranded, re-themed, and rewired to the shared Cedar bundle. The interception and overlay code predates this project. We would rather say that than have you discover it in the commit history.

One policy. Every door.

The endpoint plane shares its Cedar bundle and its detector tiers with the agent and file planes — because it is the same person's data whichever way it leaves.
